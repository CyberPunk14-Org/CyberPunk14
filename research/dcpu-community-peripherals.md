# Community peripheral prior art for DCPU-16

## Scope

This review covers the 0x10c Standards Committee repository and the TechCompliant (TC-Specs) community hardware catalogue, alongside the archived DCPU-16 v1.7 hardware interface. These sources are historical community proposals/specifications, not additions to the official v1.7 set. [0x10c Standards Committee README](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae36ab84bce4dae02f26519e915469ce400/README.md) · [TC-Specs repository](https://github.com/techcompliant/TC-Specs/tree/a7289f204d4c9abcd6b153479e33000567eb8e29) · [DCPU-16 v1.7 hardware](https://github.com/lucaspiller/dcpu-specifications/blob/e154827c56664ad4a92ac2d404c6c21583ffee04/dcpu16.txt#L149-L154)

## Networking and inter-machine communication

- **The KaiComm HIC is in TC-Specs, not the 0x10c Standards Committee repository.** The committee README reserves `NET` and `HW` areas, but the checked repository snapshot has a networking draft and no HIC hardware specification; the HIC's own spec is under TC-Specs. [0x10c Standards Committee README](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae36ab84bce4dae02f26519e915469ce400/README.md) · [0x10c Standards Committee tree](https://github.com/0x10cStandardsCommittee/0x10c-Standards/tree/47c8bae36ab84bce4dae02f26519e915469ce400) · [KaiComm HIC](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/IO%20Data/KaiComm-HIC.md#L13-L33)
- **0x10c's networking document is a physical/link-layer draft, not a network peripheral standard.** It proposes multiple CPUs sharing a bus with separate data, permission-to-send and acknowledgement signals; it explicitly leaves data routing/addressing out of scope. It was written against DCPU-16 v1.1 assumptions—including no CPU interrupts—so it should be treated as historical protocol prior art, not a v1.7-compatible hardware definition. [Draft OSI Physical Layer, status and assumptions](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae36ab84bce4dae02f26519e915469ce400/NET/Draft_OSI_Physical_Layer.txt#L1-L17) · [scope and addressing](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae36ab84bce4dae02f26519e915469ce400/NET/Draft_OSI_Physical_Layer.txt#L59-L68) · [v1.1 assumptions and three signals](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae36ab84bce4dae02f26519e915469ce400/NET/Draft_OSI_Physical_Layer.txt#L115-L137) · [signal protocol](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae36ab84bce4dae02f26519e915469ce400/NET/Draft_OSI_Physical_Layer.txt#L171-L217)
- **KaiComm HIC** is a multiport bidirectional data interface: the spec assigns one hardware ID to 8-, 16-, and 32-port versions, differentiating them by version. It defines port status, word-level receive/transmit, receive and transmit interrupts, and an eight-word port-name lookup. Receive buffering is per port, while transmission is shared and serialized; this gives a useful device/port abstraction, but the specification does not define a higher-level addressed network or routing protocol. [KaiComm HIC identity and topology](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/IO%20Data/KaiComm-HIC.md#L13-L28) · [commands and port interface](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/IO%20Data/KaiComm-HIC.md#L30-L86)
- **Other communication examples:** KaiComm RCI is a half-duplex radio datagram device with configurable channel/power, one incoming and outgoing datagram buffer, and broadcast delivery to other stations on the same channel; it does not specify per-recipient addressing. KaiComm SSI defines a bidirectional synchronous serial link with selectable word size and baud. Together these are examples of distinct link-level devices, not one universal network API. [KaiComm RCI](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/IO%20Data/KaiComm-RCI.md#L13-L35) · [KaiComm SSI](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/IO%20Data/KaiComm-SSI.md#L13-L48)

## Sensors and general I/O

- TC-Specs includes a gas chromatograph sensor family with gas identification, concentrations and pressure readings. One model communicates over HIC and another directly through DCPU hardware interrupts; analyses take seconds, illustrating a stateful, slow sensor rather than a synchronous read-only register. [LifeSys GCA](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/Sensors/LifeSYS-GCA3623.md#L13-L55)
- For general input, the VeXXaN DACA exposes four analog axes and sixteen digital buttons; its spec polls analog/digital state separately and interrupts on button changes, not analog changes. For output, the Vartok speaker provides two independently settable frequency channels. [DACA](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/Input/daca.md#L14-L61) · [speaker](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/Simple%20Outputs/speaker.md#L8-L28)
- TC also proposed a device-type taxonomy for sensors, human-interface devices, output-only devices, wireless devices, and wired communications, with class/subclass/API/capability fields and a vendor-specific device portion. This is TC's own convention, not a requirement of DCPU-16 v1.7. [TC device types](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/device-type.md#L5-L25) · [classes and subclasses](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/device-type.md#L28-L74)

## Hardware/manufacturer IDs and collision practice

- **The v1.7 contract:** `HWQ` returns the 32-bit hardware ID in A:B, the 16-bit version in C, and the 32-bit manufacturer ID in X:Y; `HWN` enumerates connected devices and `HWI` addresses one by its enumeration index. The specification defines these fields and per-device behavior, but does not prescribe a global allocation/registration scheme for IDs. [DCPU-16 v1.7 hardware query and hardware model](https://github.com/lucaspiller/dcpu-specifications/blob/e154827c56664ad4a92ac2d404c6c21583ffee04/dcpu16.txt#L149-L154) · [hardware enumeration](https://github.com/lucaspiller/dcpu-specifications/blob/e154827c56664ad4a92ac2d404c6c21583ffee04/dcpu16.txt#L195-L206)
- **TC's precedent:** its `TC-IDs.md` is a human-maintained “currently used IDs” table pairing 32-bit vendor codes with 32-bit device IDs and versions; individual specs use the same fields. The TC type-code document further suggests a vendor-unique lower device-ID field, but TC does not document an allocator or a process that guarantees uniqueness. [TC ID table](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/TC-IDs.md#L1-L50) · [TC device type encoding](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/device-type.md#L5-L25)
- **There are concrete collision/compatibility warnings.** The TC table gives the same manufacturer, hardware ID (`0x3846BC64`) and version (`0x6673`) to both its Otec radar and tracking theodolite. It also lists different IDs for devices named Generic Timer, Generic ASCII Keyboard, and LEM1802 than the official specs do. Do not treat this community table as an authoritative registry or copy its IDs blindly. [TC duplicates and entries](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/TC-IDs.md#L3-L10) · [duplicate Otec entries](https://github.com/techcompliant/TC-Specs/blob/a7289f204d4c9abcd6b153479e33000567eb8e29/TC-IDs.md#L32-L34) · [official Generic Clock](https://github.com/lucaspiller/dcpu-specifications/blob/e154827c56664ad4a92ac2d404c6c21583ffee04/clock.txt#L1-L3) · [official Generic Keyboard](https://github.com/lucaspiller/dcpu-specifications/blob/e154827c56664ad4a92ac2d404c6c21583ffee04/keyboard.txt#L1-L3) · [official LEM1802](https://github.com/lucaspiller/dcpu-specifications/blob/e154827c56664ad4a92ac2d404c6c21583ffee04/lem1802.txt#L7-L10)
- **Recommendation for the CyberPunk14 catalogue:** reserve one explicit project-owned manufacturer ID for game-specific peripherals, allocate a distinct stable hardware ID (and version) to each device, and keep a checked-in registry with automated uniqueness checks on `(manufacturer ID, hardware ID)`. Check that registry against v1.7 official IDs and published community IDs before assigning values; treat the TC type taxonomy as optional inspiration only. This is a project-level collision convention, not a guarantee of global uniqueness: the v1.7 spec and reviewed community catalogues expose no central allocator, and TC's own list contains a duplicate.
