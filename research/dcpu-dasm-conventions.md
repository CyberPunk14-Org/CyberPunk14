# DASM dialect, files, boot, and compatibility

## Findings and recommendation

There is no official DCPU-16 assembler language or portable `.bin`/`.dcpu16` container. The community calls the source language DASM, but implementations diverge; the 0x10c Standards Committee's 0xSCA document is explicitly a voluntary syntax proposal, not a standard. [Archive README](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/README.md) · [0xSCA proposal](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/ASM/Spec_0xSCA.txt)

For the in-game assembler, recommend a deliberately small, documented, deterministic dialect: accept common `:label` and `label:` forms; case-insensitive mnemonics/registers but preserve case in identifiers and strings; support forward references and a local-label convention; `DAT` emits 16-bit words, with strings expanded to one character per word and no implicit terminator; `;` line comments; and explicit (not silently assumed) string terminators. Implement a separate, small preprocessor for relative includes and parameterized macros if game content needs them. Do not imply `.org`, `.include`, macro syntax, expression grammar, or binary byte order are universally compatible; gate these by documentation/tests. The community sources below show each varies by assembler. [0xSCA proposal](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/ASM/Spec_0xSCA.txt) · [Swetland assembler](https://github.com/swetland/dcpu16/blob/9f7baf5/assembler.c) · [dcpu16py assembler](https://github.com/jtauber/dcpu16py/blob/89acf95/asm.py) · [DCPUB README](https://github.com/Blecki/DCPUB/blob/ceb330a/readme.md)

Keep the emulated floppy as raw words/sectors, per the map. Treat any exported/imported byte stream as a separately specified format with an explicit byte order; do not infer it from `.bin` or `.dcpu16`. The CPU specification's little-endian recommendation concerns multi-word values in DCPU memory, not a universal byte serialization for assembler output. [DCPU-16 v1.7 spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/dcpu16.txt) · [archive README](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/README.md)

Do not bake in a boot signature or filesystem as a property of the drive. The DCPU spec does not define a floppy boot protocol; the M35FD is operated by software issuing sector-read/write HWIs. The Standards Committee's disk-controller text is a draft proposal, while BBOS defines its own boot convention and BBFS its own layout. Preserve raw-sector hardware and implement any selected boot/filesystem in shipped DCPU software. [M35FD spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/m35fd.txt) · [disk-controller draft](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/ASM/Draft_DCPU-16_Disk_Controller_KK1000.txt) · [BBOS docs](https://github.com/MadMockers/BareBonesOS/blob/e093c6a/README.txt) · [BBFS README](https://github.com/interfect/bbfs/blob/3fe6836/README.md)

For compatibility checks, use the official DCPU sample plus the `dcpu16-tests` assembly corpus for CPU/assembler basics; then test representative peripheral/software stacks: DCPUB's `helloworld`, `spacesnake`, LEM/keyboard/M35FD and BFS512 tests; AtlasOS for a larger keyboard/screen/process OS; and BBOS with BBFS's bootloader and test program for boot, sector I/O, and filesystem behavior. These are distinct legacy targets, not a claim of one shared ABI. [DCPU-16 spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/dcpu16.txt) · [dcpu16-tests](https://github.com/krasin/dcpu16-tests/tree/3f89b0b) · [DCPUB programs/tests](https://github.com/Blecki/DCPUB/tree/ceb330a/Binaries/techcompliant) · [AtlasOS README](https://github.com/0x10cAtlas/AtlasOS/blob/3cd2d09/README) · [BBFS README](https://github.com/interfect/bbfs/blob/3fe6836/README.md)

## Source dialect: conventions versus actual assemblers

The official v1.7 document specifies the CPU instruction set and recommends little-endian ordering for multi-word data in programs, but does not specify an assembler grammar. The archive README says no official assembler was released and describes the NASM-like family as “DASM”; it lists `.dasm`/`.dasm16` source and `.bin`/`.dcpu`/`.dcpu16` object extensions as community usage, not a file-format contract. [CPU spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/dcpu16.txt) · [archive README](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/README.md)

The committee's 0xSCA proposal is useful as a candidate baseline but is expressly “not a standard.” It specifies case-insensitive syntax except within strings/character literals; semicolon comments; labels ending in `:` and local labels prefixed with `_` and scoped by global labels; `.include`/`.incbin`; `.def`/`.define`/`.equ`; `.dw`, `.dp`, `.fill`, `.ascii`; `.org`; macro and repeat blocks; conditional assembly; and arithmetic/bitwise/logical expressions. Its strings have configurable word/byte packing flags, so that proposal itself is broader than a simple common-denominator assembler. [0xSCA proposal, sections 3–6](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/ASM/Spec_0xSCA.txt)

Actual assemblers are not interchangeable:

| Implementation | Evidence of dialect / limits |
| --- | --- |
| [Brian Swetland's C assembler](https://github.com/swetland/dcpu16/blob/9f7baf5/assembler.c) | Accepts both `label:` and `:label`; folds identifiers and resolves labels case-insensitively. Its data aliases include `DAT`, `DATA`, `DW`, and `WORD`; quoted strings become one word per character. Its parser has a small early opcode set, not the full v1.7 instruction set. It has no general expression, include, macro, or `.org` grammar. |
| [jtauber/dcpu16py](https://github.com/jtauber/dcpu16py/blob/89acf95/asm.py) | Requires a colon-prefixed label (`:name`) at the start of a line; recognizes all-uppercase or all-lowercase mnemonics/registers rather than arbitrary mixed case; labels are looked up with case preserved. `DAT` accepts numbers and quoted strings, with strings expanded one character per word. Its grammar has no `.org`, include, macro, or expression directives. |
| [jaspervdj/dcpu16-hs](https://github.com/jaspervdj/dcpu16-hs/blob/7598f08/src/Assembler/Parser.hs) | Uses colon-prefixed labels and exact-case mnemonic/register parsers (`SET`, `A`, etc.). Its parsed statement model consists of instructions and labels; it is a narrower dialect than 0xSCA. |
| [DCPUB](https://github.com/Blecki/DCPUB/blob/ceb330a/readme.md) | The compiler has a separate preprocessor which expands includes/macros; its README requires preprocessing before compilation when preprocessor directives are used. Its inline assembly grammar supports labels and `DAT`. Its binary emitter defaults to little-endian words and has a big-endian option. This is an example of preprocessor behavior belonging to a toolchain, not a universal DASM rule. [Preprocessor implementation](https://github.com/Blecki/DCPUB/blob/ceb330a/DCPUB/Preprocessor/Parser.cs) · [binary emitter](https://github.com/Blecki/DCPUB/blob/ceb330a/DCPUBCL/Program.cs) |

In practice, `DAT` is an assembler pseudo-op, not a CPU opcode. Community examples commonly use `DAT "text", 0` for word-per-character, zero-terminated strings, but assemblers differ on accepted aliases and string packing. For example, the two assemblers above emit each string character as an individual word, whereas 0xSCA proposes selectable packed/unpacked ASCII. The `DAT` examples in [AtlasOS's VFS table](https://github.com/0x10cAtlas/AtlasOS/blob/3cd2d09/misc/vfs.dasm16) also explicitly pad and terminate strings where needed. There is no safe assumption that a quoted string is automatically packed or terminated. [Swetland assembler](https://github.com/swetland/dcpu16/blob/9f7baf5/assembler.c) · [dcpu16py assembler](https://github.com/jtauber/dcpu16py/blob/89acf95/asm.py) · [0xSCA proposal](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/ASM/Spec_0xSCA.txt)

## Binary word order

There is no universal byte order attached to `.bin`/`.dcpu16`. The archive lists those extensions but defines no serialization. Concrete examples conflict: `dcpu16py` writes each word using big-endian `>H`; `dcpu16-hs` serializes words with `fromWord16sbe`; Swetland's binary output writes the in-memory `uint16_t` directly and even marks host-endian handling as unfinished; DCPUB defaults to little-endian and exposes `--big-endian`. These are incompatible byte streams for the same word program. [archive README](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/README.md) · [dcpu16py](https://github.com/jtauber/dcpu16py/blob/89acf95/asm.py) · [Haskell assembler](https://github.com/jaspervdj/dcpu16-hs/blob/7598f08/src/Assembler.hs) · [C assembler](https://github.com/swetland/dcpu16/blob/9f7baf5/assembler.c) · [DCPUB README](https://github.com/Blecki/DCPUB/blob/ceb330a/readme.md) · [DCPUB emitter](https://github.com/Blecki/DCPUB/blob/ceb330a/DCPUBCL/Program.cs)

## Floppy boot and filesystem conventions

The DCPU specification gives no built-in boot sequence; M35FD software selects a sector and destination RAM address through HWI. I found no standalone/adopted bootloader specification in the 0x10c Standards Committee repository; its closest boot-related document is a draft disk-controller proposal which *envisions* a reset-time read of side 0/track 0/sector 0 into address 0, where software then begins. It is explicitly a draft for a proposed controller, not a contract of the CPU or the official M35FD. The historical official M35FD instead defines software-triggered sector reads and writes. [committee repository](https://github.com/0x10cStandardsCommittee/0x10c-Standards/tree/47c8bae) · [DCPU spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/dcpu16.txt) · [M35FD spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/m35fd.txt) · [controller draft](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/ASM/Draft_DCPU-16_Disk_Controller_KK1000.txt)

BBOS is a concrete OS-specific convention: its docs say to scan supported drives, accept a sector 0 whose word at `0x1FF` is `0x55AA`, load that sector at address 0, set register A to the drive number, then jump to 0. BBFS layers its own “Bootable Bfs512” format on that: sector 0 is the loader; sector 1 begins the filesystem header/free map/FAT; its bootloader loads `BOOT.IMG`. BBFS describes itself as based on DCPUB's BFS512 and says later BFS512 added sector-0 boot support, making the formats compatible on M35FD disks. These are useful compatibility targets, but BBOS's signature/API and BBFS layout are not part of the hardware spec. [BBOS bootloader/API document](https://github.com/MadMockers/BareBonesOS/blob/e093c6a/README.txt) · [BBFS README](https://github.com/interfect/bbfs/blob/3fe6836/README.md) · [DCPUB BFS512 implementation](https://github.com/Blecki/DCPUB/tree/ceb330a/Binaries/techcompliant)

A separate community filesystem proposal is HAT (Harry's Allocation Table) in the Standards Committee repo. It describes a sector-based lower layer and inode/link directories above it, with raw sector payloads; the document is a draft, not a universal disk format. Therefore, there is no single community filesystem to require for raw floppy compatibility. [HAT draft](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/FS/Draft_Harrys_Allocation_Table.txt) · [committee repository README](https://github.com/0x10cStandardsCommittee/0x10c-Standards/blob/47c8bae/README.md)

## Suggested compatibility suite

1. **Instruction/assembler baseline:** assemble and run the official v1.7 example, then the community [dcpu16-tests](https://github.com/krasin/dcpu16-tests/tree/3f89b0b) corpus. The latter identifies itself as tests for DCPU assemblers and interpreters. Add local cases for both label spellings, forward labels, packed-vs-word strings, comments, `DAT`, and the chosen expression/preprocessor subset. [official CPU spec](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/dcpu16.txt) · [test corpus](https://github.com/krasin/dcpu16-tests/tree/3f89b0b)
2. **Peripheral programs:** use DCPUB's code examples and tests, especially `helloworld`, `spacesnake`, `lem`, `keyboard`, `m35fd`, and `test-bfs512`; its README says it targets v1.7 and includes an emulator and sample code. This provides executable usage of display/input/storage, not just CPU instructions. [DCPUB README](https://github.com/Blecki/DCPUB/blob/ceb330a/readme.md) · [program/test directory](https://github.com/Blecki/DCPUB/tree/ceb330a/Binaries/techcompliant)
3. **OS smoke tests:** AtlasOS documents cooperative multitasking, process loading, keyboard/display routines, and a virtual filesystem; it is useful for CPU, screen, keyboard, interrupts, and process behavior, but its real floppy filesystem is listed as planned. [AtlasOS README](https://github.com/0x10cAtlas/AtlasOS/blob/3cd2d09/README) · [AtlasOS source](https://github.com/0x10cAtlas/AtlasOS/tree/3cd2d09)
4. **Boot/storage integration:** run BBOS with BBFS's bootloader and `bbfs_test.asm`; BBFS says its test formats the disk, installs its loader, saves itself as `BOOT.IMG`, and verifies first-boot and later BBFS-boot paths. [BBOS](https://github.com/MadMockers/BareBonesOS/tree/e093c6a) · [BBFS README](https://github.com/interfect/bbfs/blob/3fe6836/README.md) · [BBFS test](https://github.com/interfect/bbfs/blob/3fe6836/bbfs_test.asm)

Older programs may assume emulator conventions rather than official device behavior: the official spec archive notes many emulators historically expose a legacy keyboard ring buffer at `0x9000` instead of the specified Keyboard HWI, and often pre-map the LEM1802. Make those compatibility shims explicit in tests, not implicit in the CPU/peripherals. [archive README](https://github.com/lucaspiller/dcpu-specifications/blob/e154827/README.md)
