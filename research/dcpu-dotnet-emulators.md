# DCPU-16 v1.7 .NET cores, assemblers, and test material

## Recommendation

Write a small, modern C# CPU core and the in-game assembler rather than adopt any candidate unchanged. **Tomato** is the strongest MIT-licensed reusable .NET core found: it has a library API, device abstraction, and code paths for the v1.7 instruction set. However, source inspection exposes interrupt-queue, conditional-cycle, and interrupt-queue-boundary errors, and its project targets .NET Framework 3.5. Treat it as a useful MIT reference or a starting point only if it is first ported and comprehensively corrected/tested. [Tomato README](https://github.com/andre-d/Tomato/blob/master/README.md) · [Tomato CPU](https://github.com/andre-d/Tomato/blob/master/Tomato/DCPU.cs) · [Tomato project](https://github.com/andre-d/Tomato/blob/master/Tomato/Tomato.csproj) · [v1.7 spec](https://github.com/lucaspiller/dcpu-specifications/blob/master/dcpu16.txt)

**Organic** is the best discovered MIT-licensed DASM assembler, but it is a feature-rich .NET Framework 3.5 command-line executable, not an emulator or drop-in modern library. It may be useful as an offline assembly/reference tool; given the stated goal of an in-machine assembler, implement that DCPU program separately. [Organic README](https://github.com/andre-d/organic/blob/master/README.md) · [Organic project](https://github.com/andre-d/organic/blob/master/Organic/Organic.csproj)

No inspected option supplies the complete target hardware set: Tomato ships only Generic Clock, Generic Keyboard, and LEM1802, while Ketchup adds M35FD and SPED-3 examples around a Tomato binary dependency. Peripheral implementations will therefore need to be built and independently checked regardless of the CPU-core decision. [Tomato README](https://github.com/andre-d/Tomato/blob/master/README.md) · [Tomato project device list](https://github.com/andre-d/Tomato/blob/master/Tomato/Tomato.csproj) · [Ketchup device modules](https://github.com/Apokee/Ketchup/tree/development/Source/Ketchup/Modules) · [Ketchup Tomato adapter](https://github.com/Apokee/Ketchup/blob/development/Source/Ketchup/Interop/TomatoDcpu16Adapter.cs)

[README](https://github.com/andre-d/Tomato/blob/master/README.md) · [LICENSE](https://github.com/andre-d/Tomato/blob/master/LICENSE) · [Device API](https://github.com/andre-d/Tomato/blob/master/Tomato/Hardware/Device.cs) · [project device list](https://github.com/andre-d/Tomato/blob/master/Tomato/Tomato.csproj) | The core implements the v1.7 opcode families, interrupt handling, cycle accounting, and hardware calls in one readable but monolithic `Execute` routine. ## Conformance and test programs

I found **no official executable v1.7 conformance suite** in the supplied specifications repository: it archives the CPU/peripheral documents, while the CPU text defines behavior rather than providing a golden test corpus. Use the v1.7 CPU table as the normative oracle for instruction semantics and cycles, and explicitly translate those rules into project-owned tests. [specification archive README](https://github.com/lucaspiller/dcpu-specifications/blob/master/README.md) · [CPU specification](https://github.com/lucaspiller/dcpu-specifications/blob/master/dcpu16.txt)

Useful but partial public test material:

- **Tomato** provides the strongest MIT-compatible implementation to differential-check against, but its discovered errors mean it is not an oracle for the affected behaviors; the repo has no CPU test project. [source](https://github.com/andre-d/Tomato/blob/master/Tomato/DCPU.cs) · [repo](https://github.com/andre-d/Tomato)
- **Encephal16** has a small interactive test harness for a v1.1 sample, explicitly not a v1.7 conformance suite. [README](https://github.com/btodoroff/Encephal16/blob/master/README.markdown) · [harness](https://github.com/btodoroff/Encephal16/blob/master/e16Test/Program.cs)
- **bartman/0x10c-tools** declares v1.7 support and has software- and hardware-interrupt programs, including a clock/HW enumeration path. These are useful smoke/regression programs, not a formally specified suite with expected final-state fixtures. [README and invocation](https://github.com/bartman/0x10c-tools/blob/master/README.md) · [software interrupts](https://github.com/bartman/0x10c-tools/blob/master/test/software-interrupts.dasm) · [hardware interrupts](https://github.com/bartman/0x10c-tools/blob/master/test/hardware-interrupts.dasm)
- **DCPU-Junk** explicitly describes its contents as miscellaneous tests rather than a conformance suite, and says the files are public domain. It includes `notch_test.dasm`, `clocktest.dasm`, `hwtest.dasm`, `m35fd.dasm`, and `testSPED3.dasm`; these can seed peripheral smoke tests, but their assertions/expected outputs must be independently established. [README](https://github.com/0x10c-crap/dcpu-junk/blob/master/README.md) · [M35FD sample](https://github.com/0x10c-crap/dcpu-junk/blob/master/m35fd.dasm) · [SPED-3 sample](https://github.com/0x10c-crap/dcpu-junk/blob/master/testSPED3.dasm) · [clock sample](https://github.com/0x10c-crap/dcpu-junk/blob/master/clocktest.dasm)
- **DCPU16.Net** and **DCPU-16-ASM.NET** have NUnit tests, but only for their own assembler/core subsets; they do not establish full v1.7 compatibility. [DCPU16.Net tests](https://github.com/pedromsantos/DCPU16.Net/tree/master/ModelTests) · [ASM.NET tests](https://github.com/densitynz/DCPU-16-ASM.NET/tree/master/DCPU16-ASM_TESTS)

For a new implementation, make deterministic state/cycle fixtures from the spec for every opcode and addressing mode, including extra-word consumption and conditional skip chains; separately test the 256/257 interrupt-queue boundary, IA==0, queued `INT`, and the “no device RAM/register mutation before its first HWI” rule. These cases follow directly from the official opcode/interrupt/hardware requirements. [opcodes/cycles](https://github.com/lucaspiller/dcpu-specifications/blob/master/dcpu16.txt#L47-L167) · [interrupt queue and IA behavior](https://github.com/lucaspiller/dcpu-specifications/blob/master/dcpu16.txt#L172-L190) · [first-HWI rule](https://github.com/lucaspiller/dcpu-specifications/blob/master/dcpu16.txt#L202-L210)

Assessment is based on repository README, licence text, project files, tests, and source inspection; I did not build or execute these legacy projects. Code quality and spec-fidelity judgments above are therefore static assessments, with concrete discrepancies linked to the relevant source.
